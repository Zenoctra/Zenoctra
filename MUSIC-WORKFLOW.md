# Scripture-to-Music: Preserving Structure Across a Data Workflow

[Portfolio](PORTFOLIO.md) / Scripture-to-music workflow

**Purpose:** Organize Bible passages, generated songs, and review outcomes across music genres while keeping passage information consistent.

**My role:** Workflow and data-model decisions, requirements, review, and contractor coordination. AI tools and contractors wrote the modern parsing, planning, database, and review implementation code.

## 1. Start from a trusted published structure

The later workflow uses published PDF and spreadsheet outlines. The source structure is scholarship I selected, not an outline authored by me or generated by the model.

I specified how to preserve heading hierarchy, derive verse ranges, handle source-specific exceptions, and merge records into canonical order. PDF indentation and spreadsheet headings needed to become explicit fields in CSV rather than disappear during extraction.

```text
Published PDF and spreadsheet outlines
  -> hierarchical CSV
  -> passage planning
  -> shared passage records
  -> song versions and reviews
```

AI supplied the parsing libraries and implementation syntax. My contribution was deciding what structure the transformation had to preserve and how the source fields should map into usable records.

## 2. Keep passage metadata separate from recordings

A passage can have several recordings, genres, or generation attempts. Copying shared passage information into every song row creates multiple places that can disagree. Counting recordings can also distort metadata that belongs to the passage itself.

I directed a PostgreSQL schema refactor to separate shared passage metadata from song versions and review outcomes, and required the consumers of that information to change with it. AI wrote the schema and query changes.

Conceptually:

```text
Shared passage information
    -> recording / song version
        -> review outcome or attempt
```

This illustrates the intended division of responsibility between records. It is not a claim that every relationship is enforced by a database constraint.

## 3. Plan lengths without discarding meaningful boundaries

The planner needs passages of workable lengths while respecting the published hierarchy. A locally attractive grouping can leave an awkward remainder and force an unnecessary split later.

My recorded contributions include the recursive outline approach, boundary priorities, the scope in which alternative groupings should be compared, and challenging unbalanced arrangements. I also worked through when an oversized neighboring section should be subdivided before merging a tiny remainder.

Gemini recommended dynamic programming and AI wrote the solver. My design decisions shaped the sections available to the solver and when additional subdivision was allowed. The workflow includes heuristics and fallbacks; it is not a proof of a universally optimal semantic partition.

## 4. Review what is actually sung

Supplying the intended lyrics during transcription risks encouraging the model to reproduce the expected words. I designed the review sequence so that the audio is transcribed without those lyrics first, then compared against the source text.

AI supplied the alignment algorithms and implementation. The audio-review component is a prototype with validation gaps; there is no independently established accuracy figure for it.

## Status and boundaries

Parsing, planning, and database components have saved implementations and outputs. The audio-review component remains a prototype. The case does not equate planned passages with verified songs or claim perfect coverage or automated QA accuracy.

The working repository remains private. No source PDFs/spreadsheets, commercial audio, generated recordings, private transcripts, local logs, or configuration files are included here.
